開場。這一章很短，但非常像 observability 的原始命題：先知道使用者看到什麼，再知道系統為什麼給他看到這些。今天先忠實把書講完，再映射到我們熟悉的 App / recommendation stack，最後才進工具與 AI。
01 · 書裡的前提

沒有 instrumentation，
就沒有可信的實驗。

要知道使用者看到了什麼、做了什麼，也要知道系統內部發生了什麼。

User

看到什麼？做了什麼？

System

哪個元件造成結果？

Baseline

正常狀態長什麼樣？

Book pp.153–156

書一開始不是教你「怎麼寫 log」，而是說：experiment 之前要先有可靠的觀測基線。對推薦系統尤其直接：CTR 掉了，到底是模型、曝光埋點、App render、API timeout，還是 experiment assignment？沒有 instrumentation 根本分不開。

04 · Multi-source logs

真正困難的是：
把不同視角串回同一件事

user / session
→
experiment
→
request
→
impression
→
click
書：需要共同 identifier。今天：通常是一組不同語義、可關聯的 IDs。

Book p.155

這一頁對 recommendation 團隊最重要。今天不會期待一個万能 join key。session_id 解 user journey、trace_id 解 causal path、request_id 解一次 serving、impression_id 解 attribution、experiment_id + variant 解實驗、model_version 解 lineage。
05 · Instrumentation culture

書最後其實講的是工程文化

No telemetry, no launch

新功能沒有觀測就不上線。

Dev owns it

開發時就把 instrumentation 一起做。

Observe telemetry

連埋點本身都要做品質監控。

Book p.156

書甚至說「沒有 logging 就像儀表壞掉的飛機」。這跟今天把 observability 放進 Definition of Done、SLO、release gate 完全是一條線。

07 · 今天的語言

同一個問題，拆成更多訊號

Events

使用者做了什麼

Logs

發生了哪些細節

Metrics

整體趨勢如何

Traces

一次請求怎麼走

Replay / RUM

使用者實際看見什麼、感受到多慢。

Evaluation

AI 系統不只要知道「發生什麼」，還要知道「做得好不好」。

工具選擇先不要從 logo 出發，而是先從「你在回答哪一類問題」出發。Events / replay 偏 product/client；logs/metrics/traces 偏 system；eval 是 AI 時代新增的品質維度。

14 · 換成我們的語言：Recommendation System

一次 Home Feed，至少有三條觀測線

Product

impression · click · dwell · conversion

System

request · latency · error · cache · trace

Model

candidate · feature · score · model version

只有三條線能對上，
你才知道「推薦變差」到底是哪一層。

這是整場最貼你們團隊背景的一頁。強調：product event、system trace、model/debug metadata 不是互相替代；它們要能 join。真正事故調查通常要在三者之間來回切。
15 · 今天的 join key，不只一個

讓每個 ID 做它該做的事

ID回答的問題
session_id這個 user journey 發生了什麼？
trace_id一次 request 在系統裡怎麼走？
feed_request_id這次推薦 serving 的完整上下文？
impression_id哪個 item 真正被曝光、點擊、轉換？
experiment_id + variant結果屬於哪個實驗配置？
model_version哪版模型產生這些分數？
這張是書中「共同 identifier」的現代翻譯。不要做一個万能 ID；用明確語義的 IDs，然後確保它們出現在能 join 的 telemetry 裡。
16 · 選工具先問問題

不要從 Logo wall 開始

「Log 怎麼搜？」

這張可以當工具定位總結。提醒大家「Grafana vs PostHog」不是公平比較，因為它們處在不同 problem space。

18 · LLM observability

HTTP 200 對 LLM 幾乎不夠

Model

provider · model · prompt version

Cost / perf

TTFT · latency · input/output tokens

Context

retrieval · tools · retry · cache

同樣是「instrumentation」，只是 request 裡多了非決定性的模型與上下文。
把它連回書，不要講成完全新世界：還是「使用者看到什麼 + 系統為什麼這樣做」。只是要記 prompt/model/retrieval/tool/cost 等新 metadata。
19 · Agent observability

Request 變成 workflow tree

user
→
agent
→
plan
→
retrieval
→
tool
→
handoff
→
final

OTel GenAI conventions 正在定義 agent / workflow / tool 等 spans；目前仍是演進中的標準。

Agent debugging 很像 distributed systems debugging：慢可能不是 model，而是 retrieval、tool、handoff、retry loop。這就是為什麼 trace tree 的模型非常自然。
20 · AI observability tools

兩套很適合拿來 demo

Langfuse
LLM / agent traces · prompts · datasets · evals
open source · self-host
Phoenix
OTel-based tracing · eval · datasets · experiments
open source

跟 Grafana / Elastic 不同：它們直接理解 prompt、token、retrieval、eval score 等 AI domain objects。

這頁把 general-purpose observability 跟 AI-specific observability 分開。不是誰取代誰；通常 production 系統仍會需要 general APM + AI trace/eval。
21 · 最重要的新差異

Observability ≠ Evaluation

Observability
What happened?

慢在哪、哪個 tool error、token 花多少。

Evaluation
Was it good?

正確嗎、grounded 嗎、task 成功嗎。

傳統 API 的 200 + latency 可以很接近「健康」。LLM 的 200 不代表答案好，所以 eval 變成一等公民。Langfuse/Phoenix 都把 online trace 與 offline dataset/experiment 串在一起。

23 · Takeaway

六年後，核心其實沒變

知道使用者經歷什麼，
知道系統為什麼這樣做，
而且兩邊能被可靠地串起來。

Book: client + server + join
→
2026: events + replay + OTel + eval
收尾就回到書。工具會換，訊號會增加，但 instrumentation 的目的沒變：讓實驗、除錯、效能與產品判斷有可以信的因果線索。
