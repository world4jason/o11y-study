13.1 · Client 與 Server 的工具化日誌

兩個視角，回答不同問題

Client

使用者看到了什麼、做了什麼，以及實際體感。

Server

系統內部發生了什麼，以及為什麼產生這個結果。

Client 比較接近 user experience；Server 比較接近 system behavior。

原書 13.1

原書先做的就是這個區分。Client 不是 Server 的替代品；兩邊各自看得到對方看不到的資訊。
13.1 · Client-side

Client 要記三類事情

操作

click · hover · scroll
何時發生、是否需要 server round-trip

效能

頁面多久顯示
多久可以互動

錯誤

JavaScript error
client crash

原書 13.1

這頁維持原書的分類：使用者操作、性能、錯誤與崩潰。App 場景的對照放到後半段再講。
13.1 · Client-side 的限制

Client log 本身也可能不可靠

成本

CPU、network、battery

Beacon loss

換頁前可能還沒送完

Trade-off

強制同步送出會增加 latency

Clock

client 時鐘可能被修改或偏移

不要直接拿 client timestamp 與 server timestamp 做時間差。

原書 13.1

這是 13.1 很重要、目前舊版簡報壓太快的地方。作者其實花不少篇幅說明 client telemetry 的成本、丟失與 clock skew。
13.1 · Server-side

Server 關心的是內部行為

Performance

response latency
哪個 component 最慢
p99

Response rate

收到多少 request
提供多少 response
retry 如何處理

System info

exception / error
cache hit rate

Server log 比較能描述系統內部原因，而且通常較少受 client network 影響。

原書 13.1

原書也舉搜尋排序分數、實際 server / data center 等例子，說明 server side 可以記錄「為什麼」產生某個結果。不過 server 之間仍要注意 clock synchronization。
13.2 · 處理多源日誌

資料來自不同地方，
但下游必須能合併

不同 Client

browser · mobile

Server

backend / service logs

不同 user state

opt-in · opt-out 等狀態

共同 identifier
+
共同欄位格式
→
下游 join / analysis

原書 13.2

作者要求一個能表示同一 user / randomization unit 的 join key；必要時還需要 event-level join key。共享格式包含 timestamp、country/region、language、platform 等 common fields。
13.3 · 工具化日誌記錄的文化

Logging 不是附加工作，
而是上線條件

沒有 log，不上線

新產品 / 新功能沒有觀測能力就不應 release。

開發時一起做

工程師在提交前就加上必要 instrumentation 並測試。

監控 log 品質

事件數、關鍵欄位、timestamp、異常值也要被檢查。

原書 13.3

作者用飛機儀表的比喻：缺少 logging 就像盲飛。這一段其實非常接近今天的 Definition of Done / release gate / telemetry quality。

AI 新增的問題

Observability ≠ Evaluation

Observability
What happened?

慢在哪、哪個 tool error、token 花多少。

Evaluation
Was it good?

正確嗎、grounded 嗎、task 成功嗎。

這是 AI 系統相對傳統 API 最重要的新增維度。可靠執行和輸出品質必須分開觀測。
