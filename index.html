Book Club · Chapter 13

Instrumentation
2020 → 2026

從「工具化日誌記錄」到 Web / App / OpenTelemetry / LLM / Agent Observability

《關鍵迭代：可信賴的線上對照實驗》 第 13 章 讀書會

核心問題：書裡的觀念哪些沒有變？哪些在 6 年後已經換了一套實作方式？

開場：這一章只有幾頁，但它其實是後面所有線上實驗可信度的地基。今天不是要說「舊書過時」，而是把它翻譯成 2026 的工程語言。
01 · 書裡真正要說什麼

先有可靠的 instrumentation，
才有可信的實驗。

你必須知道使用者看到了什麼、做了什麼，也要知道系統內部發生了什麼。

Client

click、hover、scroll、頁面顯示時間、互動、JS error / crash。

Server

response latency、p99、request volume、exception、cache hit。

Join

不同來源的 log 要能透過共同 identifier 串回同一個 user / randomization unit / event。

Source：第 13 章 pp.153–156。這裡刻意沿用書中的 client / server / join framing。

書裡的重點不是「寫 log」本身，而是 experiment data 的可解釋性。如果 user 看到 A，但 server 記成 B，A/B test 結果再漂亮也沒意義。
02 · 當時的典型做法

Instrumentation ≈ 事件埋點 + Server log + 自己把資料接起來

關注點書中描述當時常見工程語言
User 行為click / hover / scroll / content viewedanalytics event / beacon
Client performance頁面顯示、可互動時間navigation timing、RUM / APM
Client reliabilityJavaScript error / crasherror reporting / crash reporting
Server healthlatency、p99、request rate、exception、cachelogs + metrics + APM
Correlation共同 join keyrequest ID / user ID / experiment ID
不要把 2020 說成「只有 log、沒有 trace」。 Jaeger、Zipkin、OpenTracing、OpenCensus 都已存在；真正還在變的是「標準化與整合程度」。
這張很重要，避免用今天的眼光過度簡化歷史。2019 年 OpenTracing + OpenCensus 已經宣布合併成 OpenTelemetry，所以這本書所在年代其實正好踩在 transition point 上。
03 · 不是舊方法消失，而是逐步標準化

從各做各的 telemetry，到共同語言

Before 2019

Logs / metrics / APM 已成熟；OpenTracing、OpenCensus、Jaeger、Zipkin 各自解決 tracing 問題。

May 2019

OpenTracing + OpenCensus 合併成 OpenTelemetry，開始把 instrumentation 與 telemetry 標準化。

2020 era

本章聚焦 online experiment 所需要的 client / server instrumentation、join key 與 log quality。

May 2026

OpenTelemetry 成為 CNCF Graduated project，成為跨 backend、跨語言的主流 open standard。

Web research：CNCF / OpenTelemetry 官方歷史資料。

可以把這張當全場的「時代定位」。本章不是落後，而是寫在觀測標準快速整合的前夜。
04 · 六年後完全沒變的四件事

1. User reality

不能只看 server 成功；要知道使用者實際看到與體感。

2. Internal cause

不能只看 UI 症狀；要知道系統內部哪個元件、哪一步造成它。

3. Correlation

多來源資料一定要能串在一起。只是今天更多時候叫 trace_id / context propagation。

4. Telemetry quality

埋點錯、漏 event、時間戳亂掉，本身就是 production bug。

變的是工具與資料模型，不是觀測的目的。

05 · Web 2026

Client logging → RUM + Product Telemetry

Product events

search_submitted
item_viewed
checkout_started

Core Web Vitals

LCP：主要內容載入
INP：互動回應
CLS：視覺穩定

RUM

real-world user、device、network、release version、route / SPA navigation。

書裡擔心「navigation 前 beacon 送不出去」的問題仍存在。現代 Web guidance 仍建議 sendBeacon() / fetch(..., keepalive:true)，並避免依賴不可靠的 unload。

今天不是只問「頁面 load 幾秒」，而是「真實使用者在什麼 route / device / release 上，哪個 interaction 變慢」。

可以直接對照原文：書說 client logging 會掉 beacon、會吃 CPU/network；web.dev 到今天仍提醒 analytics code 自己不能造成 long task，這是非常漂亮的「舊問題仍然存在，只是 API/慣例更成熟」。
06 · App 2026

從 crash log，變成 user-perceived performance

Startup

cold / warm start、foreground / background。

Rendering

screen render、slow / frozen frames、jank。

Network

HTTP latency、payload、endpoint breakdown。

Reliability

Crash、ANR，以及「正在使用時真的被使用者感受到」的 crash / ANR rate。

觀測焦點從「程式有沒有 crash」向「使用者到底感受到什麼」移動。

Firebase Performance Monitoring 是一個很好的現代化例子：startup、screen render、network 都能自動形成 trace；Android Vitals 甚至把 user-perceived crash / ANR 視為核心品質指標。

10 · Agent 時代的新邊界：MCP

Tool call 甚至跨越 transport / process / vendor

過去

server → internal function

同一個應用內比較容易追。

現在

agent → MCP client → MCP server → tool

Context 必須跨 JSON-RPC / stdio / Streamable HTTP 傳遞。

OpenTelemetry 已開始定義 MCP client / server span、operation duration、session duration 與 context propagation。

這一塊仍在快速演進：GenAI / Agent / MCP semantic conventions 目前仍有 Development 標記，所以概念可採用，但 schema 要版本化。
11 · LLM / Agent 最大的新變化

Observability ≠ Evaluation

Observability 回答
What happened?

哪一步慢？哪個 tool fail？用了多少 token？哪個 model / prompt version？

Evaluation 回答
Was it good?

正確嗎？grounded 嗎？tool 選對嗎？task 完成嗎？使用者滿意嗎？

Production traces
→
Failure examples
→
Dataset
→
Offline eval
→

→

傳統 HTTP service 的 200 + latency 正常，通常至少代表系統有工作；LLM 的 200 只代表模型回了東西。因此 AI 系統必須把「運作狀態」與「輸出品質」分開量。

14 · Takeaways

三句話帶走

① 原則沒過時

沒有可靠 instrumentation，就沒有可信的 experiment / diagnosis。

② Join key 變成 trace

從 client / server log correlation，走到跨服務、跨 AI workflow 的 context propagation。

③ AI 多了一個維度

「有成功執行」與「回答得好」是兩件不同的事，所以 observability 必須和 evaluation 接起來。

真正沒有改變的是：你要能解釋使用者看到的結果，是怎麼被系統產生出來的。
