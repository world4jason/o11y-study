13.1 · Client 與 Server 的工具化日誌

兩個視角，回答不同問題

Client

使用者看到了什麼、做了什麼，以及實際體感。

Server

系統內部發生了什麼，以及為什麼產生這個結果。

Client 比較接近 user experience；Server 比較接近 system behavior。

原書 13.1

Client 不是 Server 的替代品；兩邊各自看得到對方看不到的資訊。
13.1 · Client-side

Client 要記三類事情

操作

click · hover · scroll
何時發生、是否需要 server round-trip

效能

頁面多久顯示
多久可以互動

錯誤

JavaScript error
client crash

Client log 本身也可能不可靠

成本

13.3 · 工具化日誌記錄的文化

Logging 不是附加工作，
而是上線條件

Web · Real User Monitoring

現在不只是「記 click」

LCP ≤ 2.5s

主要內容多久顯示

INP ≤ 200ms

互動後多久有畫面反應

CLS ≤ 0.1

頁面會不會亂跳

看真實使用者資料的 p75；SPA 還要處理 route / soft navigation，而不是只量第一次 page load。
Core Web Vitals 目前仍是 LCP、INP、CLS，門檻看第 75 百分位。Chrome 151 在 2026 加入 soft-navigation APIs，讓 SPA route transition 能更像獨立 navigation 來量。
Web · 一次 user journey

Client telemetry 現在更像一段旅程

└─ Navigation / Route

   │  └─ Backend distributed trace
   └─ Product events

書裡的 beacon loss / telemetry overhead 問題沒有消失，只是 SDK、batching、RUM 與 browser API 更成熟。

OpenTelemetry

不只 trace：還有共同的語義

Traces

operation / parent-child

Metrics

可聚合的量化訊號

Logs

事件與診斷細節

Profiles

profiling semantic conventions

HTTP、DB、messaging、feature flags 等都有 semantic conventions；跨語言 / 跨團隊不用各自發明欄位。
OpenTelemetry semantic conventions 已涵蓋 traces、metrics、logs、profiles、resources；但各 category 的穩定度不一定相同。
一個 2026 還要注意的現況

Browser OTel instrumentation
仍是 experimental / mostly unspecified

Frontend
成熟 RUM / Product SDK

Events · Web Vitals · Replay · Errors

Backend
OpenTelemetry

Trace context · spans · metrics · logs

透過 trace context 串起兩側，不必為了「全 OTel」硬把 Browser 端所有 telemetry 自己做。
這是 OpenTelemetry 官方目前的警告。Frontend 與 backend 可以不同 SDK，但用 context/correlation 接起來。

AI 的新差異

Observability ≠ Evaluation

Observability
What happened?

慢在哪、tool 是否失敗、token 花多少。

Evaluation
Was it good?

correctness · groundedness · task success · user feedback

這是 AI 系統真正多出來的一個維度：健康不等於品質。
